# Контекст и векторная память D&D/НРИ

## Архитектура

Пайплайн D&D и пользовательской НРИ использует одну выбранную LLM для игровых ответов и существующий локальный embedding-сервер. Чанкинг, метаданные, BM25, объединение результатов, ранжирование, бюджет и экстрактивная сводка выполняются в Node.js. Дополнительной модели ранжирования и LLM-вызовов для поиска нет. Системные инструкции D&D не переписываются.

Ранее архив нарезался по символам, поиск по лору возвращал ID целой записи, а лексический поиск архива включался лишь при отказе embeddings. Найденная середина большой записи могла не попасть в промпт. Теперь поиск возвращает конкретные фрагменты с происхождением; общий бюджет ограничивает именно эти фрагменты.

```text
выбранный лор + валидная память + архив этой комнаты
  → смысловые чанки и метаданные
  → фильтрация области/типа
  → независимые BM25 top-10 и cosine top-10
  → объединение и ранжирование JS
  → системные инструкции / состояние / текущие заявки и недавние посты
  → до 3 найденных фрагментов, до 1500 токенов вместе с обёртками
  → проверка фактического окна локальной LLM
  → генерация
```

Правила из Rule book остаются отдельной частью обязательных инструкций. Они не индексируются как события мира. Лор выбирается по `room.lorebookIds`. Одиночные чаты, фанфики и другие комнаты не становятся источниками этой партии.

## TypeScript API

Канонический исходный код находится в `server/rag/ts/`:

Общий импорт: `server/rag/index.mjs`; типы доступны через сгенерированные `.d.mts`. Node запускает скомпилированные `.mjs`, поэтому ему не требуется поддержка исполнения TypeScript. Команда `npm run build:server` проверяет типы и обновляет runtime. `node scripts/build-rag.mjs --check` проверяет соответствие runtime исходникам. Обычная сборка и сборка Windows-пакета выполняют этот шаг автоматически.

Полный пример на TypeScript: [examples/dnd-memory-pipeline.mts](../examples/dnd-memory-pipeline.mts). Он принимает существующий encoder и серверный игровой адаптер, не создаёт дополнительные модели.

## Чанкинг и метаданные

```ts
const chunks = chunkLorebook(text, {
  maxTokens: 480,
  modelTokenLimit: 512,
  overlap: 50,
  source: 'Лорбук Северной гавани',
  documentId: 'npc-arvin',
  scope: 'room:campaign-id',
  lorebookType: 'npc',
});
```

Абзац сохраняется целиком, если помещается; длинный абзац делится по предложениям. Перекрытие состоит из целых предложений и занимает **не более 50 токенов**: точные 50 могут потребовать разрыва предложения. Если одно предложение превышает весь лимит, применяется разбиение по словам, а для чрезмерно длинного слова — по Unicode-кодовым точкам. Это отмечается в `metadata.segmentation`. Исходные UTF-16 смещения позволяют восстановить текст без потерь.

Размер никогда не превышает минимум `maxTokens`, `modelTokenLimit` и 512. `calculateTokenBudget` использует локальный `js-tiktoken/lite` с `cl100k_base`; таблица загружается при первом использовании, а не при запуске приложения. Это токенизатор, не третья модель. Его подсчёт точен для указанной кодировки, но отличается от токенизаторов GGUF. Асинхронный `chunkLorebookAsync` принимает собственный счётчик embedding-сервера.

Документация используемой библиотеки: [js-tiktoken](https://github.com/dqbd/tiktoken/tree/main/js).

Для встроенного `sas-embedding` сервер использует этот асинхронный путь: фактический предел — `min(512, embeddingTokenLimit − 8)`, включая подсчёт специальных токенов. `metadata.tokenization` показывает `native`. Идентичность файла модели, лимит и токенизатор входят в ключ кэша. При отказе нативного счётчика текущий поиск переходит на BM25; непроверенные чанки не отправляются encoder и перепроверяются при следующем запросе. Для стороннего локального API без встроенного токенизатора подсчёт остаётся приближённым, что отражается предупреждением. Только лор с включённой векторизацией передаётся encoder.

Типы — `npc`, `location`, `spell`, `item`, `lore`, `quest`. `extractMetadata` использует заголовки, указанный тип лорбука, словарь признаков и консервативные правила извлечения имён/ключевых слов на русском и английском. Это эвристика: явные корректные метаданные предпочтительнее предположений. Происхождение содержит `source`, `scope`, ID документа, хеш редакции, смещения и вид источника. Логический индекс связывает эти метаданные с фрагментом; существующий дисковый кэш хранит векторы по идентичности encoder и тексту. После перезапуска метаданные восстанавливаются из сохранённых источников; новая полная копия текста партии на диск не создаётся ради индекса.

## Поиск и параметры

```ts
const results = await hybridSearch(query, sceneState, {
  chunks, scope: 'room:campaign-id', type: ['npc', 'quest'],
  embed: texts => embeddings.vectors(state, texts, signal),
  vectorTopK: 10, keywordTopK: 10, topK: 20, signal,
});
```

Фильтры применяются до подсчёта BM25 и передачи текста encoder. Невекторизуемый лор участвует только в BM25. Отключение векторной памяти оставляет лексический поиск; ошибка encoder также не выключает BM25. Отмена запроса прерывает поиск.

BM25 использует `k1=1.2`, `b=0.75`, частоты документов и нормализацию результата в диапазон 0–1. Cosine ограничен диапазоном 0–1. После объединения списков:

```text
finalScore = 0.6 × vectorScore + 0.4 × keywordScore + 0.2 × entityBonus
entityBonus = 0.2, если metadata.name присутствует среди сущностей сцены; иначе 0
```

Таким образом, прибавка за присутствующую сущность составляет **0.04**. Сравниваются нормализованные целые имена/фразы, а не случайные подстроки: Арвин и Арвинд различаются. Простое упоминание NPC внутри другой записи не даёт ей бонус. Имена и редкие слова поддерживает независимый BM25; семантику — encoder. Веса — начальные параметры, а не универсальная оценка качества любой модели.

Встроенный сервис кэширует разбиение неизменённых документов в ограниченном manifest. Изменения, удаления, выключение книги и смена encoder инвалидируют соответствующую часть. Перечитывание векторного кэша не означает повторный инференс encoder. Корпус и BM25 всё ещё просматриваются при запросе: кэш не превращает этот алгоритм в ANN-индекс и не гарантирует постоянное время на неограниченной истории.

Объём кэша разбиения ограничен восемью комнатами, 4096 источниками на комнату и 16000 фрагментами суммарно. Эти границы ограничивают удерживаемый кэш, а не удаляют игровые источники из сохранения. При первом обращении к большой истории подготовка дороже, чем повторный запрос. Токенизатор encoder имеет отдельный ограниченный LRU.

## Бюджет

`assemblePrompt(context)` возвращает строку. `assemblePromptDetailed(context)` также возвращает сообщения, выбранные фрагменты и статистику. Системный текст и JSON-состояние не обрезаются. Последнее сообщение сохраняется; более старая история добавляется полными сообщениями в предпочтительный бюджет 800 токенов. RAG получает остаток, максимум 1500 токенов и три чанка. Обёртки и метаданные тоже учитываются.

Дополнительно соблюдаются отдельные квоты `maxLoreTokens` и `maxMemoryTokens`. В комнате они берутся из `memorySettings.loreBudget` и `memorySettings.memoryBudget`; архивные события делят квоту с памятью. Нулевой бюджет исключает категорию ещё до векторизации, включая постоянный лор. Эти квоты не увеличивают общий предел 1500. Новые настройки применяются к новой генерации; сохранённый контекст дописывания остаётся снимком прежнего запроса.

В действующем мультиплеере используется `budgetGameMessages`: все текущие заявки игроков и подтверждённые результаты движка остаются обязательными. Уже существующий контекст последних четырёх постов защищён независимо от RAG. Финальная проверка через токенизатор локальной LLM удаляет целые низкоприоритетные RAG-фрагменты, а не части JSON или инструкций. Продолжение и перегенерация используют прежний снимок источников.

Рекомендуемый старт: окно 8192, ответ 1024, чанки 480/перекрытие50, история около800, RAG1500/3. На малом окне полезно снизить ответ и RAG. Реальный системный контракт SAS заметно больше условных 300 токенов: при нехватке обязательного контекста сервер выдаёт ошибку вместо молчаливой потери правил или игрока. Нулевая квота RAG при длинной обязательной сцене — ожидаемое следствие приоритетов.

## Обработка JSON без смены промпта

`parseLLMResponse` принимает чистый JSON, fenced JSON и однозначный объект с внешним текстом. Структура проверяется type guards; несколько конфликтующих объектов, дубли ключей, запрещённые поля и неверные параметры отклоняются. Обычный художественный ответ совместим со старым режимом как `action_required:'none'`. Некорректный структурированный ответ не превращается в механическое действие или публичный сырой JSON.

`thinking` — ограниченная служебная строка до 512 символов для краткой заметки/плана. Сервер не требует раскрытия внутреннего хода рассуждений модели и не сохраняет эту строку в истории, памяти, экспорте, отчёте контекста или последующем запросе.

```ts
const parsed = parseLLMResponse(raw);
if (responseParseError(parsed)) throw new Error('Некорректный ответ');
const result = executeAction(parsed, serverOwnedEngine);
// result содержит narrative_text и результат движка; thinking здесь нет.
```

`executeAction` синхронный; для асинхронного адаптера есть `executeActionAsync`. `action_required:'none'` возвращает повествование без действий. Остальные варианты вызывают `rollDice(params)` или `updateState(params)` и возвращают `ActionResult`.

В SAS адаптер [gm-json-engine.mjs](../server/gm-json-engine.mjs) проверяет свежую комнату, фазу, разрешённого NPC/задание и серверный ID операции. `target` для `roll_dice` — ID заранее подготовленной проверки; результат считает существующий движок. Нельзя подставить готовое число, перебросить уже выполненное действие или бросить за игрока вне его очереди. Для запроса проверки игрока требуется обычный интерфейс подготовки/ожидания его броска.

`update_state` разрешает только явно включённые строковые поля сцены `notes`, `weather`, `time`, `description`. Произвольные пути JSON, HP, инвентарь, правила и очередь недоступны. Возможности расширяются отдельными валидированными доменными командами, а не общим `Object.assign` состояния партии.

[gm-structured-narration.mjs](../server/gm-structured-narration.mjs) запрашивает JSON на том же подключении. Для встроенного llama.cpp используется прямая GBNF-грамматика [gm-json-grammar.mjs](../server/gm-json-grammar.mjs): она исключает отдельный канал рассуждений, который Gemma может открывать вопреки `enable_thinking: false` при `response_format`. План остаётся только в приватном поле `thinking` (до 160 символов грамматики); системный промпт не изменяется. Для внешнего API сохраняется `response_format` с JSON Schema и одна попытка без формата при его неподдержке. Сырой ответ буферизуется на сервере: клиент не получает промежуточные JSON-поля. При действии выполняется не более одного механического запроса, затем результат движка передаётся той же LLM для итогового повествования. Цепочки новых действий отклоняются; проверка ответа обязательна при любом транспорте.

Формат включается отдельно, чтобы не менять работающую генерацию у существующих пользователей. API хоста: `PUT /api/multiplayer/settings`, с сохранением остальных текущих `aiSettings`:

```json
{
  "aiSettings": {
    "structuredNarration": true,
    "allowNarrativeSceneUpdates": false
  }
}
```

`allowNarrativeSceneUpdates` по умолчанию выключен. Перегенерация и дописывание выполняются без механических действий. Если действие уже выполнено, а последующий запрос оборвался, результат закрепляется до продолжения; перезапуск не даёт нового броска или повторного изменения сцены.

Разрешённые виды действий отражаются и в формате ответа: `roll_dice` доступен только при нерешённой проверке NPC, `update_state` — при включённом разрешении на изменение полей сцены. После первого действия, при перегенерации и дописывании допускается только `none`. Серверная проверка возможностей остаётся обязательной и не полагается на соблюдение формата моделью. Пробелы между JSON-полями ограничены четырьмя символами, чтобы модель не могла потратить весь лимит на пустые строки.

## Точки интеграции и диагностика

- [room-memory.mjs](../server/room-memory.mjs): область комнаты, экстрактивная сводка, вызов нового поиска только для D&D/НРИ.
- [game-rag.mjs](../server/game-rag.mjs): выбранные документы, кэш чанков, локальный encoder и гибридный поиск.
- [prompt.mjs](../server/prompt.mjs): при готовом game-RAG не вставляет повторно целые записи лора/памяти.
- [multiplayer.mjs](../server/multiplayer.mjs): защищённый игровой контекст, общий бюджет, снимок, JSON-адаптер и проверка ответа.
- [room-narration.mjs](../server/room-narration.mjs): проверка реального окна и исключение целых RAG-записей.

`contextReport.rag` показывает выбранные ID, число фрагментов, бюджет и статистику поиска/кэша. `sources` отражает фактически включённые источники. `vectorStatus` и warnings объясняют лексический fallback. Эти поля не содержат `thinking`.

Новые проверки находятся в `tests/rag-*.test.mjs`, `tests/game-rag.test.mjs`, `tests/gm-json-engine.test.mjs`, `tests/gm-structured-narration.test.mjs`; интеграционные сценарии — в `tests/room-narration.test.mjs`. Они включают изоляцию комнат, длинный лор, Unicode, отмену, отказы encoder, лимиты, защиту состояния и восстановление после разрыва.
